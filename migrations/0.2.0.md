# 0.2.0 — Metadata service + visual dashboards

Human-readable companion to `migrations/0.2.0.yaml`. The advisor reads both; this
file is the *why* a maintainer writes once and reviews in the PR.

## What changed
Loom now talks to a real Metaflow **metadata service** instead of local
`~/.metaflow` files. The local stack (on the existing minikube) gains:

- a **metadata service** + its Postgres — every run registers here, and the
  Metaflow Client API reads it (`METAFLOW_DEFAULT_METADATA=service`);
- the **visual Metaflow UI** (`metaflow-ui`) at `:3000` — runs, DAGs, timelines,
  artifacts — fronted by an in-cluster `/api` proxy so the browser needs one
  port-forward;
- `loom doctor` gains a **metadata-service `/ping` check** that WARNs if you're
  still on local file-based metadata.

## Why `loom update` alone isn't enough
`loom update` only refreshes **code** (git pull + npm rebuild + `pip install -e .`).
It does not touch the cluster, regenerate `.env.metaflow`, or start port-forwards.
The migration manifest carries that variable, machine-specific reasoning — re-run
the setup script (idempotent; deploys the new services alongside your existing
minio and rewrites `.env.metaflow` to `metadata=service`), re-source the env,
and bring up the two new port-forwards (`:8080`, `:3000`).

## What to expect (not failures)
- **Old runs won't appear.** Anything tracked before the flip lived as flat files
  in `~/.metaflow`, never registered to a DB — there's no backfill. Only runs after
  the flip show in the service/UI. An empty dashboard right after migrating is
  normal.
- **Postgres is `emptyDir`.** Run history (and minio data) doesn't survive a
  `minikube stop/start` or pod restart. Fine for local dev; use a PVC for
  persistence.
- **A Pending `metaflow-ui` pod** means the one-time native UI build was skipped or
  failed — the metadata service still works; finish the build and the pod starts.

## First-update bootstrap (one-time)
`loom update` self-rebuilds the CLI, but the `loom update` you run is the *old*
compiled build — so the **first** update onto a migrate-capable release can't run
the migration step itself (that code only exists after the rebuild). After that
first `loom update`, either run **`loom update` once more** or **`loom migrate`
directly**, and from then on every `loom update` reconciles automatically. If you'd
rather not wait, the migration is just the deterministic setup — run it directly:

```bash
bash scripts/setup_metaflow_minikube.sh && source .env.metaflow && loom doctor
```

## The heavy step
The first time, the setup script builds the `metaflow-ui` SPA from source
(`Netflix/metaflow-ui` `v1.3.14`) — natively for arm64, a few minutes, automatic
and non-fatal. Later runs reuse the loaded image.
